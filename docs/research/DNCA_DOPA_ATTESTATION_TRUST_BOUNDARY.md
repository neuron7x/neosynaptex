# DNCA / DOPA HMAC Attestation Boundary — Experimental v1

## Purpose and assurance level

A SHA-256 checksum identifies bytes but cannot establish **who** authored them.
This change adds HMAC-SHA256 over a canonical, content-bound run manifest.
A verifier can reject post-sealing changes to the routing report, the
per-claim route, the committed claim content, and the exact YAML configuration.

**HMAC does not prove that a claim is true, that the signed route is sound,
or that the signer is independent.** The trust guarantee is conditional on
the MAC key being generated, stored and used only in a trusted execution
principal outside the agent and allocator.

## First-principles separation

- **Generator / DNCA** selects candidate hypotheses; untrusted by default.
- **Allocator** reserves and prioritizes verification; it does not close claims.
- **Attestor** takes completed run artifacts and protects their provenance
  using a secret key unavailable to the agent. It must enforce caller/source
  authorization before sealing; the helper function does **not** enforce
  operating-system access control by itself.
- **Arithmetic verifier** validates content, route conditions and optionally
  an HMAC-authenticated run, then recomputes the limited integer statement.
- **Experiment judge** separately evaluates effectiveness and false closures
  with ground truth and fully metered cost; not implemented here.

The new functions are:
`core/eai/dopa_run_attestation.py::seal_arithmetic_run` and
`verify_arithmetic_run_attestation`.

The optional interface
`verify_scheduled_arithmetic(run_dir, claim, attestation_key=trusted_key)`
must reject missing/incorrect attestations and must not write a receipt
on rejection. Existing calls without a key still produce exact arithmetic
receipts, but carry `archive_authentication=UNATTESTED`.

## Binding semantics

Define:

- `H(x)`: SHA-256 digest of exact byte sequence `x`.
- `K`: secret key, at least 32 random bytes, provisioned out-of-band.
- `J(m)`: strict canonical JSON of dictionary `m` (sorted keys, stable separators).
- `R`: raw bytes of the final run report.
- `Q`: raw bytes of the per-claim routing record.
- `C`: raw bytes of the saved configuration.
- `d`: precommitted SHA-256 of the original arithmetic claim.

Manifest `m` binds the protocol domain, run ID, claim ID, `d`,
`H(R)`, `H(Q)`, and `H(C)`. Its MAC is:

```text
T = HMAC-SHA256(K, J(m))
```

The verifier re-derives all fields **from current archived input files**,
requires their equality with the signed manifest, and compares the supplied
MAC using constant-time `hmac.compare_digest` on equal-form digests.

This is origin-authentication *relative to the holder of K*, **not**
asymmetric digital signing or non-repudiation.

## Threat model

| Attack | Intended reaction |
|---|---|
| Modify route after sealing | Reject |
| Modify all route/report data consistently | Reject by MAC-bound digests |
| Swap claim content/answer | Reject by precommitted claim hash |
| Modify exact YAML configuration | Reject by config digest |
| Use arbitrary forged MAC | Reject |
| Reuse a wrong key | Reject |
| Publish a second attestation at same path | Fail without overwrite |
| Replace critical input with symlink | Reject (best effort) |
| Give attacker access to K | **Outside guarantee: compromised trust boundary** |
| Re-sign a forged run with trusted K | **Outside guarantee: signer authorization failure** |
| Control interpreter/process memory or directory race | **Outside guarantee** |
| Change files before the trusted attestor accepts them | Must be prevented by trusted signer policy |

## Deployment preconditions

1. Generate a 32-byte (minimum) cryptographically random key in a trusted
   secret manager, **not** a source file, repository secret printed in logs
   or a string generated by the LLM.
2. Run an attestor in an isolated OS/container identity with read-only access
   to sealed candidate archives and restricted write permissions for only
   the attestation destination.
3. Do not expose the key to the agent or any routing/plugin tool.
4. Run the verifier with the independently provisioned key.
5. Keep the system fail-closed if key, attestation, config snapshot, payload
   commitment or independent verifier execution is unavailable.
6. Rotate credentials after suspected compromise, identify key version
   in an external inventory, and invalidate artifacts in the compromised epoch.
7. Export receipts to an independently access-controlled append-only evidence
   store for real production provenance; local files alone are insufficient.

## Residual issues

The code currently exposes `seal_arithmetic_run` as a callable Python
helper. **Software calling the helper is not automatically a trusted
signer.** The OS-level isolation and independent issuance policy are
deployment requirements, not repository-enforced controls. The filesystem
checks are not race-free against adversarial concurrent writes; current
HMAC attestations lack a key ID/version and a separate issuance policy.
Nominal budget reservations remain distinct from actual CPU/GPU/token spend.
DNCA's salience-based routing benefit remains UNTESTED.

**⊛ Quintessence:** A hash binds content. A secret-key MAC binds content to
an authorized key-holder. Neither substitutes for an independent proof of
the original proposition or for experimental verification of system benefit.
